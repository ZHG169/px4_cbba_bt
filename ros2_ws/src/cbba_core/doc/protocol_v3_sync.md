# 協定版本 3：壓縮狀態摘要＋明確缺口請求＋受限分批回覆（2026-10-28）

版本 2 的整體設計（`protocol.md`）不變，版本 3 只改「補發」（anti-entropy）。版本 2 和 3 互相拒收（表頭的 version），
全隊要一起升級；目前跑版本 2 的只有我們自己的節點（伯宇還在版本 1），所以現在升版本的代價最低。

## 一、為什麼改

版本 2 的補發（`CbbaComm::resendMissing`）：鄰居的 round_key 和我不同時，比對它上一次收齊的 CBBA_STATE 紀錄，補它缺的。
CBBA_STATE 只放**進行中**的任務，所以每一個**已結束**的任務在對方的紀錄裡都「沒有列」——分不出它不認得，還是早就知道結束了，
只好每個都補（TASK_ANNOUNCE＋TASK_CLOSE），每個任務每秒最多一次（`resend_gap`），**沒有總量上限**。

只要有新任務或結束通知在路上，摘要就不同；掉包時一不一致就是好幾秒。結果：mesh 流量和「已結束的任務數」成正比
（`itest.py loss` 70%：每個掉包率重開節點 13 kB/s；同一個掉包率 150 次、累積 1350 個任務 78 kB/s；
不重開、一路累積時 10%～50% 是 74～98 kB/s）。實機上任務越跑越多、已結束的又永遠記著，流量會一直漲，
弱網時大量補發還會擠掉真正需要送的封包。

## 二、做法

```
CBBA_STATE 帶壓縮摘要（每個建立者一筆 14 B）
   │ 收到：和我的摘要逐筆比對（round_key 相同就跳過）
   ├─ 某個建立者不同 → 送 GAP_REQUEST 給那個鄰居：「建立者 X、流水號 a～b，我每個的狀態是這張點陣圖」
   │                    ↓ 鄰居比對點陣圖，只把我缺的放進補發佇列
   └─ 同時把那個建立者「最近 push_recent_sec 內變動過」的任務直接放進補發佇列（不等請求：高掉包時一來一回很難成功）
補發佇列 → SYNC_BATCH（一個封包裝多筆任務定義、結束紀錄，≤ max_packet），token bucket 限速（repair_rate）
```

| 部分 | 做法 | 原因 |
|---|---|---|
| 壓縮摘要 | task_id = 建立者 × 65536 + 流水號，同一個建立者的流水號大致連續。每個建立者一筆：建立者、最小流水號、最大流水號、知道幾個、已結束幾個、CRC-32（流水號＋是否已結束） | 大小只和建立者數有關（3 台＋3 隻狗 6 筆 = 84 B），不隨任務數長大；哪個建立者不同一眼看得出來 |
| 什麼時候帶摘要 | flags bit 1。距上次帶 ≥ `digest_period`（1 s）、自己的 round_key 變了、或有存活鄰居的 round_key 和我不同時才帶 | 收斂後不用每 200 ms 帶；不一致時每次都帶，對方馬上能比 |
| 摘要是不是最新的 | 帶摘要那一則的 round_key 就是摘要對應的狀態；收到的一方記下來，只有「它最新的 round_key ＝ 摘要那時的 round_key」才拿來比 | 舊摘要不會造成誤判 |
| 缺口請求 GAP_REQUEST（種類 7） | 目標鄰居、建立者、起始流水號、筆數、點陣圖（每個流水號 2 bit：0 不認得、1 進行中、2 已結束）。一次最多 4000 個流水號（1000 B），範圍更大時下次接著問。同一個（鄰居, 建立者）每 `gap_request_gap`（0.5 s）最多一次 | 回答的一方只補對方真正缺的；請求很小，雙方都問（各自補自己缺的），不用先決定誰比較新 |
| 回答 | 只有被指名的鄰居回答。逐一比對：我知道、對方不認得 → 任務定義；我已結束、對方不認得或進行中 → 結束紀錄（不認得時兩個都補） | 只補缺的 |
| 直接推送 | 某個建立者和鄰居不同時，自己那個建立者在 `push_recent_sec`（10 s）內新增或結束的任務，不等請求就放進補發佇列；同一個任務每 `resend_gap`（1 s）最多一次 | 最常見的不一致是「剛建立、剛結束、還在路上」；高掉包時請求＋回覆都成功的機率是單向的平方（70% 時約 9%），推送是單向的 |
| 分批回覆 SYNC_BATCH（種類 8） | 筆數＋多筆（種類 1 B、長度 2 B、內容）。內容就是 TASK_ANNOUNCE／TASK_CLOSE 去掉 20 B 表頭的部分（含轉送區塊、原本的 origin），用原本的解碼、權限檢查 | 一個封包裝多筆，省表頭；格式和驗證都沿用 |
| 限速 | token bucket：`repair_rate`（預設 8000 B/s）、`repair_burst`（2400 B）。佇列分兩級：進行中的任務先、已結束的後 | 補發流量有上限，不會擠掉 CBBA_STATE、完成確認 |
| 套用 | SYNC_BATCH 的每一筆照 TASK_ANNOUNCE／TASK_CLOSE 處理（權限檢查、先到的 TASK_CLOSE 暫存），但**不轉送**，並登記到去重複（之後同一則的轉送不再處理） | 只在直接鄰居之間補；多跳時一跳一跳補（中間那台補齊後，它和下一台的摘要又不同） |
| 不變的 | 建立時的 TASK_ANNOUNCE、完成三種封包照舊（會轉送）；每 5 s 保底重播一個任務照舊；round_key 照舊（開機同步、完成宣告用） | 只換掉補發 |

拿掉的：`resendMissing`（摘要不同就把所有已結束的任務各補一次）。

## 三、封包格式（版本 3）

表頭的 version = 3，其他不變。

**CBBA_STATE（種類 2）**：在 part_count 之後多一段摘要。

```
表頭 20 | round_key 4 | exchange_step 2 | flags 1 | stable_steps 1 | snapshot_id 2 | part_index 1 | part_count 1 |
digest_count 1 | (creator 2 + min_seq 2 + max_seq 2 + known 2 + closed 2 + crc 4) × D |
stamp_count 2 | (agent_id 2 + stamp_ms 4) × N |
record_count 2 | (task_id 4 + winner_id 2 + winning_bid 4 + assign_version 8 + assignee_id 2 + assign_state 1) × R
大小 = 20 + 17 + 14D + 6N + 21R
```

flags：bit 0 參與出價、**bit 1 有摘要**（沒有時 D = 0；有摘要而 D = 0 表示「一個任務都不知道」）。
有摘要時每一批都帶（和 s 一樣），分批計算時算在固定大小裡。

**GAP_REQUEST（種類 7，不轉送）**

```
表頭 20 | target_id 2 | creator 2 | first_seq 2 | count 2 | bitmap ⌈count / 4⌉
```

點陣圖從 first_seq 開始，每個流水號 2 bit（高位在前）：0 不認得、1 進行中、2 已結束（3 保留，拒收）。count 1～4000。

**SYNC_BATCH（種類 8，不轉送）**

```
表頭 20 | item_count 1 | (type 1 + length 2 + 內容 length) × M
```

type 只能是 3（TASK_ANNOUNCE）或 6（TASK_CLOSE）；內容是那種封包表頭之後的全部（轉送區塊＋欄位），解碼時補一個表頭交給原本的解碼函式。

## 四、參數（`CommConfig`）

| 參數 | 預設 | 說明 |
|---|---|---|
| `digest_period` | 1.0 s | 收斂後多久帶一次摘要 |
| `gap_request_gap` | 0.5 s | 同一個（鄰居, 建立者）的缺口請求最短間隔 |
| `push_recent_sec` | 10 s | 摘要不同時，直接推送這麼久之內新增、結束的任務 |
| `repair_rate` | 8000 B/s | 補發（SYNC_BATCH）的平均上限 |
| `repair_burst` | 2400 B | token bucket 的容量（約 2 個滿的封包） |
| `resend_gap` | 1.0 s | 同一個任務直接推送的最短間隔（沿用） |
