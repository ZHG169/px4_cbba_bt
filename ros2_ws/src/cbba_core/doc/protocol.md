# 機間通訊協定 版本 2

cbba_core · 2026-10-09 · 狀態：**實作完成、單元測試與真 UDP 整合測試通過，還沒在 SITL 跑**

版本 1 照「機間通訊封包規格」2026-10-06 的格式。版本 2 **不相容於規格書**：每筆任務資料都帶 uint32 task_id，
不再用 AGENT_STATE 裡 z、y 陣列的位置代表全隊共用的任務編號。版本 1 和版本 2 的節點不能互通
（magic、version 不同會被拒收），全隊要一起升級。

逐位元組的格式寫在各標頭檔的開頭：`wire_header.hpp`、`wire_agent_state.hpp`、`wire_cbba_state.hpp`、
`wire_task_announce.hpp`、`wire_completion.hpp`。這份文件寫整體設計和為什麼。

---

## 一、為什麼改

版本 1 的 AGENT_STATE 用陣列位置當任務識別：`z[49]`、`y[49]` 是「任務編號 49」的得標者和得標價。
所有節點要先同意「49 是哪個任務」才能交換資訊，因此：

| 版本 1 的限制 | 原因 |
|---|---|
| 機號超過 8 的載具（狗 50）不能建立任務 | 任務編號依機號交錯切份：第 k 台用 (k−1)+8j。50 的 49 = uav2 的 1+8×6 |
| 每台一輩子只能建立約 32 個任務 | 任務編號是 uint8（0～254），切成 8 份，已完成的不回收 |
| 完成確認不會等機號超過 8 的載具 | 鄰居、存活名單是 8 個位元 |
| 重開機要先和鄰居同步才敢自編號碼 | 怕撞到還沒補到的編號 |
| 重開機要把 seq 存在檔案裡（seq_file） | 從 0 開始的話，鄰居的去重複會把新封包當舊的丟掉 |

版本 2：封包裡每筆任務資料都帶 task_id，各節點自己維護 task_id → 本機資料的對照。上面的限制都不存在；
容量只受記憶體、封包大小限制（CBBA_STATE 每筆 10 B，任務多時分批）。

## 二、封包總覽

所有封包共用 20 B 表頭，網路位元組順序（大端序），逐欄位寫入（不直接傳 struct 的記憶體，沒有補位）。

| 種類 | 名稱 | 內容 | 大小 | 什麼時候送 | 轉送 |
|---|---|---|---|---|---|
| 1 | AGENT_STATE | 參與出價、遙測、飛行狀態（armed／offboard／landed）、位置、電量、BT 的執行狀態（狀態、可否中斷、預估剩餘時間）、執行中與保留的任務和版本、路徑、鄰居 | 74 + 4L + 2K | 每 0.5 s | 否 |
| 2 | CBBA_STATE | round_key、各任務的得標者與得標價、**最新的正式指派（版本、執行者、狀態）**、時間戳 s | 36 + 6N + 21R，每批 ≤ 1200 B | 每 200 ms；表有變動時立即；和鄰居不一致時每 50 ms | 否 |
| 3 | TASK_ANNOUNCE | 任務定義（task_id、類型、位置、價值、建立時刻、截止時刻、執行時間） | 65 | 建立時；補發、每 5 s 保底重播 | 是 |
| 4 | COMPLETION | 完成宣告（帶指派版本） | 53 + 2V | 回報完成時；沒收齊每 1 s 重送 | 是 |
| 5 | COMPLETION_ACK | 完成確認（接受／不認得／指派已過期） | 54 + 2V | 收到宣告時 | 需要時 |
| 6 | TASK_CLOSE | 任務結束（完成；取消），帶 actor 與指派版本 | 55 + 2V + 6K | 收齊確認時、取消時；補發 | 是 |

L = 路徑長度、K = 鄰居數或確認數、N = s 的筆數、R = 紀錄數、V = 存活名單長度。

### 表頭（20 B）

| 欄位 | 型別 | 說明 |
|---|---|---|
| magic | uint16 | 0x4342（"CB"） |
| version | uint8 | 2 |
| type | uint8 | 上表的種類 |
| sender_id | uint16 | 直接發送者（轉送時是轉送者）。0 保留為「無人」，0xFFFF 保留 |
| session_id | uint64 | 每次節點啟動隨機產生 |
| sequence | uint32 | 同一個 session 內的序號，所有種類共用一個計數器 |
| payload_length | uint16 | 表頭之後的位元組數，要等於實際長度 |

session_id + sequence 只用來丟掉重複、過期的封包和辨識轉送事件，**不是任務指派版本，也不取代 CBBA 的時間戳 s**。

### 轉送區塊（14 B，TASK_ANNOUNCE、COMPLETION、COMPLETION_ACK、TASK_CLOSE）

origin_id 2 | origin_session 8 | origin_seq 4。轉送 = 換上自己的表頭，payload 原封不動；
去重複的鍵是（種類, origin_id, origin_session, origin_seq）。

### CBBA_STATE 的紀錄（每筆 21 B）

| 欄位 | 型別 |
|---|---|
| task_id | uint32 |
| winner_id | uint16（0 = 無人得標，和現有程式一致） |
| winning_bid | float32 |
| assign_version | uint64（這個任務最新的正式指派版本，見第五節） |
| assignee_id | uint16（那次正式指派的執行者；0 = 撤銷或還沒指派過） |
| assign_state | uint8（0 無、1 待接受、2 保留、3 執行中；2、3 會鎖定：別台不出價） |

只放**自己認得、而且還在進行**的任務。不認得或已結束的不放（版本 1 用 y = −1 表示）。
s 是（機號 2 B + 時間 4 B）的清單，**每一批都帶完整的 s**。

## 三、接收端的處理順序

1. 驗證表頭：magic、版本、種類、sender_id、payload_length 等於實際長度。解碼時再驗證筆數、欄位範圍
   （task_id 的建立者不能是 0、得標價是有限的非負數、part_index < part_count…）。
2. **session 過濾**：每個發送者一個滑動視窗（4096 號，像 IPsec 的 anti-replay）。視窗內沒收過的接受
   （亂序到達的也接受），收過的、比視窗還舊的丟掉。新的 session = 重開機，接受並把舊的記成退役；
   退役 session 的封包（重開機前、在網路上延遲的）丟掉。
3. **狀態的新舊**由內容判斷：CBBA_STATE 的 snapshot_id 比已收到的舊就整批丟掉；AGENT_STATE 的 sequence 比上一則舊就丟掉。
4. **轉送事件去重複**：同一則事件只處理、轉送一次（記 60 s）。
5. 用 task_id 查本機的任務：
   - TASK_ANNOUNCE：不認得就加入；認得但 origin 不同 → `task_conflicts`（兩台用了同一個機號），保留先收到的。
   - CBBA_STATE 的紀錄：還不認得的任務略過（見第五節第 2 點）。
   - TASK_CLOSE：還不認得的任務先暫存，任務到了再套用。
6. 交給原本的 CBBA 規則（Choi 2009 的 17 條）判斷，**不直接覆寫本機結果**。

## 四、分批

CBBA_STATE 每批（整個 UDP 封包）不超過 `max_packet`（預設 1200 B）：
每批 (1200 − 36 − 6N) / 21 筆紀錄，5 台時每批 54 筆。分批欄位：snapshot_id、part_index、part_count、record_count。

- 每收到一批就直接交給 CBBA 規則：規則是逐任務判斷的，只看那個任務的 z、y 和 s，而每批都帶完整的 s。
- 收斂判定、補發要比對「對方知道哪些任務」，只用**收齊**的那一次。缺批時等下一次（每 200 ms），
  不會把缺少的紀錄當成任務被刪掉（`incomplete_snapshots` 記數）。

## 五、正式指派、接受、搶占、排隊（2026-10-09）

CBBA 的得標只是候選；**地面端（BT）保有最終的接受與中斷權**。火警優先級高，不代表能覆蓋地面端的安全判斷。
流程在 `assignment_manager.hpp`，核心的位置限制在 `cbba_agent.hpp` 的 `ExecConstraints`。

### 正式指派的版本與狀態

| 項目 | 做法 |
|---|---|
| 版本 | 每個任務一個版本（uint64）、全隊共用。**請 BT 接受時就預先分配**（已知的最新版本 + 1，狀態「待接受」），當作這次請求的識別碼；接受後同一個版本變成「保留」或「執行中」 |
| 作廢 | 拒絕、逾時、撤銷（任務換掉、搶占、執行失敗、之後的 constraint）時產生新版本（執行者 0、狀態「無」）。作廢的版本不再使用 |
| 傳遞 | 放在 CBBA_STATE 的每筆紀錄裡；各節點取（版本, 狀態, 執行者）較大的那筆。同版本時已接受的勝過待接受的（兩台同時產生同一個版本、其中一台還不知道另一台已接受） |
| 鎖定 | 別台「保留」或「執行中」的任務：不出價。持有者自己的核心也不讓別台的得標資訊把它拿走（剛加入、還不知道鎖定的那台會在收到鎖定後撤回）。**待接受不鎖** |
| 解鎖 | 持有者撤銷、執行失敗 → 重新開放競標；完成、取消 → 永久關閉；**持有者失聯 → 照樣鎖著**，`lockedByLostAgents()` 列出、節點印「失聯：待確認」，不重新指派（失聯接手另外做） |

### 和 BT 的握手（`require_accept`：狗預設 true，無人機預設 false）

| 話題 | 方向 | 內容 |
|---|---|---|
| `/<ns>/exec_state`（ExecState） | BT → CBBA | 執行狀態（閒置、前往、處置中、不可中斷、停止中、故障）、`preemptible`、`estimated_remaining_time`、有沒有執行中／排隊中的任務（旗標＋task_id＋版本）。逾時用本機收到的單調時間判斷（`exec_timeout` 1.5 s） |
| `/<ns>/assignment_request`（AssignmentRequest） | CBBA → BT | ACTIVATE（現在執行；`preempt` = 要中斷目前的任務）、RESERVE（排隊保留）、RELEASE（先前的請求或保留作廢） |
| `/<ns>/assignment_response`（AssignmentResponse） | BT → CBBA | task_id、版本、接受／拒絕、原因（暫時／永久）、detail |
| `/<ns>/assigned_task`（Task） | CBBA → BT | 接受後才發：執行中的正式指派，帶版本 |

```
路徑第一個任務連續 assign_hold（0.6 s）沒變
  → 待接受：預先分配版本，送 ACTIVATE；舊的任務照常執行，assigned_task 不變（黑板不覆寫）
  → BT 停止舊的、完成交接，回覆接受 → 執行中，發 assigned_task
  → 拒絕：暫時 → 撤回出價，BT 的執行狀態改變時重新評估；永久 → 不再出價
  → accept_timeout（3 s）沒回覆：當成暫時拒絕、送 RELEASE；之後才到的接受回覆忽略（版本已作廢）
```

`require_accept = false` 只是跳過握手（請求當下就算接受），可行性、版本、回報檢查照常。
`accept_timeout` 是故障處理的上限，不是正常的反應時間。

### 能不能指派（地面端狀態表）

令新任務 j、目前的任務 k：Accept = F_ij ∧ [Idle_i ∨ (P_j > P_k ∧ Preemptible_i)]。優先級：本機安全處置（BT 內部）＞ 火警 ＞ 一般巡檢，同級不搶占。

| 地面 agent 的狀態 | 新火警 |
|---|---|
| 閒置，能力、電量、路徑符合 | 可以 |
| 一般巡檢、可以安全中斷 | 可以：ACTIVATE 帶 `preempt`，BT 停止巡檢、交接後才切換；巡檢撤銷這次指派、任務保留（不送 TASK_CLOSE） |
| 正在處理另一個火警 | 不切換：排在後面（保留），或交給別台 |
| 不可中斷階段 | 暫時不能：只排隊；BT 回報可以中斷（`preemptible` 變 true）時馬上重新評估，保留的火警排到前面、送 ACTIVATE |
| 故障、電量不足、不可達 | 不可以：故障時不加入新任務，還沒被接受的出價全部撤回 |

### 排隊

- 執行中任務之後最多保留 **1 個**火警（`max_queued_fires`），經過 BT 接受（RESERVE），全隊看得到（狀態「保留」、會鎖定）。
- 可行性：now + 預估剩餘時間 + 前往 + 處置 ≤ d_j。有期限時 d_j = 期限；沒有期限時 d_j = **建立時刻** + `max_queue_wait`（120 s），
  建立時刻放在 TASK_ANNOUNCE 裡，各節點、每輪競標都一樣，不會重新起算。
- 預估剩餘時間不知道（ExecState 的負值、或沒有 ExecState）時不接受排隊。
- 排隊不等於立即執行：執行中的任務結束、保留的排到第一時，核心重新檢查可行性，通過才轉成執行中（版本不變，不再問 BT）。
  等待中做不完了（剩餘時間變長）→ 釋放、撤銷保留、送 RELEASE。

### 回報與任務結束的權限

| 項目 | 做法 |
|---|---|
| BT 回報 | `task_result` 的 task_id 和版本要是目前「執行中」的正式指派，否則拒絕、任務狀態不變（X→Y→X 時 X 第一次的版本已經舊了） |
| 完成宣告 | COMPLETION 帶版本。收到的節點知道更新的版本 → ACK status 2（指派已過期），這次完成作廢、任務保留 |
| 完成的 TASK_CLOSE | actor 是執行者自己（等於 origin_id），版本不比收到的節點知道的舊。不合的不結束、不轉送（`rejected_closes`） |
| 取消的 TASK_CLOSE | `/<ns>/cancel_task` 發起。actor 要是任務的建立者，或在 `cancel_authorities`（全隊要一樣）裡。收到的節點也檢查 |
| 執行失敗 | 不送 TASK_CLOSE：撤銷指派（新版本）、任務保留、自己不再出價，由 CBBA 重新分配 |

### 分段量測

每個開始執行的指派，節點印一行：建立 → 排第一 → 請求 → 接受 → 發布 assigned_task → BT 回報執行（ExecState 的版本）。
2026-10-09 的真 UDP 整合測試（假的 BT 以 10 Hz 回覆、回報 ExecState）：

| 段落 | 量到 | 說明 |
|---|---|---|
| 建立 → 排第一 | 約 15 ms | UDP＋共識 |
| 排第一 → 請求 | 600～610 ms | `assign_hold` |
| 請求 → 接受 | 64～134 ms（中斷時 344 ms） | 假 BT 的回覆延遲（50 ms，中斷 300 ms）＋ 10 Hz 迴圈 |
| 接受 → 發布 | 0 ms | |
| 發布 → BT 回報執行 | 約 105 ms | 假 BT 的 ExecState 是 10 Hz |
| 合計 | 約 790～870 ms | **目前不能宣稱符合 300 ms**；主要是 assign_hold |

`assign_hold` 先維持 0.6 s。要調低時，要一起驗證會不會造成指派震盪（協商途中排第一的任務來回）。

### 之後加 constraints

競標前、正式指派前、執行期間的檢查都接在這裡：constraint 觸發撤銷時讓目前的正式指派失效（撤銷 = 新版本），
重新指派時產生新版本，回報與權限檢查不用改。

## 六、和 2026-10-09 的建議不同、或建議沒寫的地方

| # | 項目 | 做法 | 原因 |
|---|---|---|---|
| 1 | 分批的處理 | 每批直接交給規則；只有收斂判定、補發等收齊 | 規則逐任務判斷、每批都有完整的 s，等收齊只會變慢；缺一批時其他批照樣生效 |
| 2 | 還沒有任務定義的紀錄 | 不暫存、不另外發「請求同步」 | 200 ms 後的下一次會再帶；對方從我的 round_key 和紀錄看得出我缺什麼，會補發 TASK_ANNOUNCE（版本 1 就有的補發） |
| 3 | 任務結束 | 保留 COMPLETION → COMPLETION_ACK 的確認流程，TASK_CLOSE 是最後的通知（取代版本 1 的「證明」） | SITL 驗證過的「全隊確認」行為不變；TASK_CLOSE 帶 reason（1 完成、2 取消） |
| 4 | 已結束任務保留多久 | 一直記著，不回收 | 忘記之後，斷線的那台補發時會把任務當新的加回來；每個任務約 100 B，記憶體不是問題 |
| 5 | 指派版本的範圍 | 每個任務一個版本、全隊共用（不是每台各自的計數器），uint64 | 收到的節點只要比「版本大小」就知道是不是舊的；正式指派紀錄跟著 CBBA_STATE 傳，不用另外的封包 |
| 6 | 無人得標 | winner_id = 0 | 和現有程式一致（0 保留為「無人」） |
| 7 | 機號 | 協定是 uint16（1～65534）；節點限制 1～254 | `RobotState.agent_id` 是 uint8 |
| 8 | 舊封包 | 滑動視窗，不是「只收比較新的」 | 一次送很多則時（大量 TASK_ANNOUNCE、分批的 CBBA_STATE）亂序很常見，只收比較新的會把先送晚到的全丟掉（測試發現） |
| 9 | 已停止參與的載具 | 收到的紀錄裡得標者是「已知停止參與」的鄰居時略過那筆 | 別台在知道它停止之前送出、晚到的訊息，會依規則把它寫回得標者，等 1.5 s 失聯才又釋放（測試發現，版本 1 也有） |
| 10 | 重開機 | session_id 取代 seq_file | 新 session 的 (origin, seq) 不會和開機前撞，不用存檔，也不受時鐘往回跳影響 |
| 11 | 先同步再送出自己的任務 | 保留（啟動後和鄰居摘要相同、或 1.5 s 沒鄰居、或等滿 5 s） | 不是為了編號，是為了查出 BT 重開機後重用 task_id（`rejected_local_tasks`） |

已知的限制：沒有認證。同一個機號用不同的 session 送封包，會被當成那台重開機（真的那台的 session 被退役、暫時收不到）；
冒名的 TASK_CLOSE 只擋得住「actor 不等於 origin」「版本舊」「沒有取消權限」這幾種。

## 六、流量

收斂後每架每秒（5 架、5 個任務、每架路徑 1 個）：

| | 版本 1 | 版本 2 |
|---|---|---|
| 共識資料 | AGENT_STATE 80 B × 5 = 400 B | CBBA_STATE 171 B × 5 = 855 B |
| 狀態 | （含在上面） | AGENT_STATE 86 B × 2 = 172 B |
| 保底重播 | 56 B / 5 s | 65 B / 5 s |
| 合計 | ≈ 411 B/s | ≈ 1040 B/s |

增加的主要是每筆紀錄多帶 task_id（4 B）、正式指派（版本 8 B、執行者 2 B、狀態 1 B），s 多帶機號（2 B），
AGENT_STATE 多了 BT 的執行狀態。任務多時版本 2 每個任務 21 B，版本 1 是 5 B，但版本 1 最多只能有 255 個任務編號，
也沒有正式指派的紀錄。

## 七、測試
