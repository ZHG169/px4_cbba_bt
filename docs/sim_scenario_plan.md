## 最終目標

> PX4 旋翼無人機，具備快速 3D 航點巡邏能力。配備下視光學／熱成像相機，當飛抵巡檢點並辨識到目標區的
> AprilTag 火情標籤且信心度達標時，判定火警成立，向全網廣播地面處置任務。

```
巡檢點任務 ─→ CBBA 分配給無人機 ─→ 3D 航點飛過去 ─→ 下視相機
                                                      ↓
     地面處置任務 ←─ 全網廣播 ←─ 判定火警 ←─ AprilTag 辨識＋信心度
     （機器狗接）
```

| 環節 | 現況（2026-10-07） |
|---|---|
| 巡檢點由 CBBA 分配給無人機 | ✅ SITL 驗證完成（分配、完成確認、失敗交回、墜毀、晚加入、重開機） |
| 快速 3D 航點巡邏 | ⚠️ 只有暫代 BT 的 `task_executor`：固定高度直線飛、沒有避碰（同高度會撞機，之後在飛行層加 CPF 之類） |
| 下視相機 | ⚠️ 機型 `gz_x500_mono_cam_down` 有下視光學相機，影像還沒接進 ROS（`gz_bridge.sh` 只送 `/clock`）；熱成像沒有 |
| AprilTag 辨識＋信心度門檻 | ❌ 還沒開始；Gazebo 場景也還沒有方塊和 tag |
| 判定火警（BT） | ❌ BT 還沒好 |
| 廣播地面處置任務 | ✅ 協定已支援：對 `/uavN/new_task` 發 `type = GROUND_INTERVENTION`，無人機不出價，狗接（`cbba_task.sh ground`） |
| 機器狗接任務 | ✅ 通用 `cbba_node`（`vehicle_type:=ugv`，dog-integration 分支），還沒在真的狗上測 |

## 二、電池權重測試（使用者提出）

同一個場景飛 **100 次**，每次搭配隨機插入的任務點，記錄「真的飛到」和「沒有飛到」的次數，比較不同電池權重。

## 三、分析：要先定清楚的地方

### 1. 任務是誰插入的（影響最大）

| 做法 | 說明 | 適合 |
|---|---|---|
| (a) 腳本插入，AprilTag 只是顯示 | 腳本決定插入點、讓 tag 顯示，同時直接發 `new_task` | **電池權重測試**：只測 CBBA，變因少 |
| (b) 無人機看到 tag 才產生任務 | 某台飛過去、辨識出 tag，才由那台發 `new_task` | 整合展示：完整的「感知 → 任務」流程，但要先有 AprilTag 偵測和 BT；「何時被發現」會變成另一個隨機因素 |

`task_id` 的建立者必須是某台無人機（地面站不是 CBBA 成員），腳本插入時要指定由哪台建立（例如離插入點最近的、或輪流）。

### 2. 「沒飛到」要怎麼分類

只記「飛到／沒飛到」的話，權重高時「沒人接」變多，看起來會像比較差。至少分成：

| 結果 | 意思 | 對電池權重 |
|---|---|---|
| 飛到並完成 | ✅ | 好 |
| 接了但沒飛到（電量不夠、觸發返航或 failsafe） | ❌ 錯誤的接單 | **權重要減少的就是這個** |
| 沒有人接（大家都電量不足、不出價） | 正確的拒絕 | 分開記，不算失敗 |
| 超過期限 | 任務太多或分配不好 | 分開記 |

### 3. PX4 SITL 的電池

- PX4 的模擬電池**依時間線性下降**，和飛多遠無關；降到 `SIM_BAT_MIN_PCT` 就停住。
- 2026-10-07 已經改成續航 900 s、最低 20%，能量模型也對齊它（見 `cbba_core/doc/parameters.md`）。
  所以出價時的預估和 PX4 回報的電量現在是一致的。
- 但要讓「沒飛到」真的發生，還需要：
  - 各台的電量不一樣（PX4 每台都從 100% 開始，可用不同的 `SIM_BAT_DRAIN` 模擬不同狀態）；
  - 設定低電量時的處置（`COM_LOW_BAT_ACT`、`BAT_CRIT_THR`），讓「電量不夠就返航」真的發生；
  - 最低電量要低於安全存量，否則電量會停在 20%，不會真的耗盡。
- 場地大小要配合電量：距離太近，電池就不是限制，權重看不出差別。

### 4. 在 Gazebo 跑 100 次的時間

一次約 3～5 分鐘（起飛＋任務 1～2 分鐘＋重置；電池要回到 100% 通常得重開 PX4）。
100 次約 5～8 小時，**這還只是一個權重**；比 3～5 個權重要好幾天。

建議分兩層：

| 層 | 用途 | 次數 |
|---|---|---|
| 離線 `cbba_sim` | 統計：每個權重 100 次以上，幾分鐘跑完 | 多 |
| Gazebo＋PX4 | 驗證：挑幾組代表性的隨機情境，確認實際飛行和離線模擬一致 | 5～10 次 |

`cbba_sim weights` 現在是**靜態分配**（一開始就給所有任務），不能動態插入、也沒有「電量用完、沒飛到」的判定，要先擴充。

### 5. 比較要公平

各權重用**同一組亂數**：第 k 次試驗不論權重多少，插入哪些點、什麼時刻插入都相同（配對比較）。

### 6. Gazebo 場景

- 8 個方塊，各自一個 tag ID（例如 tag36h11 的 0～7）。
- tag 大小配合飛行高度：5 m 高、下視相機，大約要 0.5～1 m 才偵測得穩。
- 「插入時才顯示」：Gazebo 執行中不容易切換顯示。可行的是插入時用 `/world/<名稱>/create` 生成 tag 模型，
  或事先把 tag 藏在方塊裡、插入時移到頂上。
- `task_executor` 目前是「進入 0.5 m 內就算到達」；如果「飛到」要以看到 tag 為準，要接 AprilTag 偵測。

## 六、原本建議的順序（1～4 已經寫好程式，2026-10-09）

1. 相機影像接進 ROS（`gz_bridge.sh` 加影像話題）
2. Gazebo 場景：3 綠＋5 紅方塊、tag、插入時顯示
3. AprilTag 偵測＋信心度門檻
4. BT 串起「到達 → 辨識 → 判定 → 廣播地面任務」
5. 擴充 `cbba_sim`（動態插入、沒飛到的判定），跑電池權重的統計；Gazebo 抽幾組驗證

電池權重測試比較適合放在 BT 串好之後。

## 七、實作（2026-10-10）

| 項目 | 檔案 | 狀態 |
|---|---|---|
| 任務點（唯一來源） | `docker/gz/worlds/patrol_site_points.csv`：G1～G3、R1～R5 的座標與 tag 編號 | ✅ |
| Gazebo 場景 | `docker/gz/gen_patrol_site.py` → `worlds/patrol_site.sdf`；tag 模型 `tag36h11_0`～`7`（1～6 是新加的，用 apriltag 函式庫產生，和現有的 0、7 逐像素相同） | ✅ 隔離的 Gazebo 載入正確 |
| terminal 輸入編號插入 | `docker/scripts/patrol_scenario.sh`（sim 容器）：互動輸入 `g`／`1`～`5`／`r`；`insert`、`replay`、`reset` | ✅ tag 生成、刪除、重放在隔離的 Gazebo 測過；發 `new_task` 要接上真的 cbba_node 才測得到 |
| 離線任務模擬 | `cbba_core/mission_sim.*`：每台跑真的 CbbaComm＋AssignmentManager（協定版本 2 封包）＋假的 BT＋PX4 式電池；`test_mission_sim` 8 項 | ✅ |
| 權重統計 | `cbba_sim insert <任務點檔>`：每個權重同一組亂數（插入時刻、耗電誤差、網路），輸出 summary／trials／tasks／agents.csv 和 `schedules/trial_NNN.csv`（給 replay） | ✅ 500 次約 13 s |
| SITL 步驟 | `cbba_core/doc/sitl_test.md` 第 6 節 | 還沒在 SITL 跑 |

模擬怎麼判斷「接了沒飛到」（`wrong_accepts`）：
- 電池照 PX4 SITL：**依時間線性下降**，待命也會耗電；出價的能量模型只估「飛行＋停留」，再加上每次試驗每台 ±`--drain-error`（預設 10%）的誤差，
  所以會出現「出價時可行、實際做不完」。
- 做不完有兩種，都算接錯：(1) 核心每秒重新評估、發現做不完 → **撤銷**執行中的指派（通常先發生）；
  (2) 電量降到 20% 時手上還有任務 → BT **返航**、回報失敗。
- 任務最後的結果分五類：完成、逾期（完成但超過期限）、接了沒飛到（failed：有人接過、最後沒完成）、
  沒人接（unassigned）、未完成（時限到還在做，正常應該是 0）。接錯之後被別台完成的，結果算完成、另外記在接錯次數。

第一次結果（預設：3 台初始電量 100／70／45 %、續航 300 s、R 點在 0～120 s 插入、每個權重 100 次）：

| 權重 | 完成 | 逾期 | 接了沒飛到 | 沒人接 | 接錯次數 | uav1／uav2／uav3 完成數 |
|---|---|---|---|---|---|---|
| 0 | 800 | 0 | 0 | 0 | 21 | 333／295／172 |
| 1 | 800 | 0 | 0 | 0 | 22 | 346／294／160 |
| 5 | 800 | 0 | 0 | 0 | 19 | 396／259／145 |
| 20 | 800 | 0 | 0 | 0 | 15 | 406／255／139 |
| 100 | 800 | 0 | 0 | 0 | 15 | 412／252／136 |

- 權重越高，工作越往電量高的 uav1 集中，接錯從 21 降到 15；接錯全部是撤銷、都發生在 uav2、uav3，任務都被別台接手完成。
- 這個場地（點之間 30～50 m）對 300 s 的續航太小，電池不是主要限制，四類結果看不出差別。要比較權重，
  要讓電池更緊：縮短續航（`--endurance`）、拉長插入時段（`--window`，待命耗電）、加大耗電誤差，或把點移遠。**這幾個值待使用者決定。**
- Gazebo 只能用不同的 `SIM_BAT_DRAIN` 做出「電量不同」（PX4 的模擬電池都從 100% 開始），對照的離線設定見 `sitl_test.md` 第 6 節。
